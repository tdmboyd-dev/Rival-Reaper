# Host command identifiers: compatibility and replay safety

Inspection: September 30, 2026. Target: existing six-team app, not a replacement. Source checkpoint: `3915e2dae769f87ed77791cf2c9be3b5f94bf926`.

## Decomposition and mapped contract

Live host actions → command identity → browser entropy provider → encoded safe command ID → authenticated session/revision-bound HTTP mutation → durable replay journal. The server owns fate randomness; a browser identifier never determines team assignment. Source owners: `examples/rival-reaper/host.js`, `src/rival-reaper/server.ts`, existing session/persistence modules.

## Primary-source findings

- W3C Web Cryptography Level 2, editor draft August 11, 2026: https://w3c.github.io/webcrypto/#Crypto-interface and https://w3c.github.io/webcrypto/#Crypto-method-getRandomValues. Inspected Crypto IDL and both random byte/UUID algorithms: UUID is secure-context restricted; byte generation has no such IDL restriction. A 16-byte Uint8Array fits the API limit. This is a draft standard, not a guarantee of a particular device implementation.
- MDN browser API documentation, inspected September 30: https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID and https://developer.mozilla.org/en-US/docs/Web/API/Crypto/getRandomValues. Corroborates origin restrictions and broad byte-generator availability. Actual intended-device behavior remains an acceptance gate.

## Candidate comparison and specification

Keep direct randomUUID: REJECT for this command path because capability absence throws before any host request. Add UUID library: REJECT, unnecessary package/supply-chain burden for an internal opaque ID. Math.random/time counter: REJECT, weaker collision behavior. ADAPT platform getRandomValues: use 16 independently generated bytes encoded as 32 lowercase hexadecimal characters. Not a UUID and no claim to be one. Both draw and advance use this function, while retries preserve the already generated command verbatim. Third-yank continuation retains the established `_name` suffix convention. If byte generation is absent or throws, send no mutation and display a supported-browser recovery instruction. No security setting, network binding, TLS behavior or permission is changed.

Production use: opaque idempotency keys attached to repeated HTTP actions. Runtime/cost: synchronous browser API, 16 bytes per new manual action, no network/provider bill. Security/privacy: no roster/token in IDs, no storage of new secrets, no transmission beyond the existing authorized host endpoint. Maintenance/license: standard browser capability; independently authored adapter, no third-party source code copied. Models, datasets and academic ranking: N/A, a browser API compatibility fix rather than a learned system. Fixtures: synthetic in-repository tests. Failure modes: missing provider, thrown generation, replay after response loss; HTTP plaintext transport remains outside this fix and must not be mistaken for a secure deployment.

## Defect, repair and evidence

RR-HOST-09: direct randomUUID calls could prevent every draw/advance on a browser origin where the method is omitted. Root cause is assuming secure-context UUID availability. Repair replaces both calls with the byte-generator adapter and explicit failure handling. Regression executes the actual host source in a VM with no randomUUID method, confirms 16-byte requests and 32-character server-compatible IDs for both actions, and confirms zero POSTs when randomness is absent. Existing replay/session/logout/third-yank regressions remain in the full suite. VM tests are not rendered-phone proof.

Acceptance: both command paths work without randomUUID; no fallback to noncryptographic entropy; missing entropy yields an actionable message and no POST; existing replay and auth tests pass. Evidence: `test/rival-reaper-host.test.ts`, `evidence/reliability-2026-09-30/tests.log`. External transport/device acceptance remains open.
